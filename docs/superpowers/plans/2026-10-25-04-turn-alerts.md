# Turn Alerts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tab titles that show the game, its player count and whether you are needed, plus notifications (in the browser and by Web Push, also on a locked phone) when it is your turn, a vote waits on you, or the game ends.

**Architecture:** One pure module, `shared/alerts.ts`, decides what a seat is needed for and the exact text. The client uses it for the tab title and for an in-browser notification when the page is hidden. The server watches each room's views after every broadcast, and on a new alert sends a payload-less Web Push signed with VAPID (`node:crypto`, keys made on first start and kept in sqlite). The service worker fetches the pending alert text from the server, shows it with one tag per game (so a newer one replaces the older), and focuses the game's tab on click.

**Tech Stack:** TypeScript, node:crypto (ES256), node:sqlite, global `fetch`, Express 5, ws, React 19, plain-JS service worker, node:test, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-25-spectators-social-and-new-games-design.md`, feature 4. Index: `docs/superpowers/plans/2026-10-25-spectators-social-and-new-games.md`. Branch `turn-alerts` from `spectators-social` after wave 2 (spectators, game-over, rematch, pass-and-play and table screen are merged). PORT 3104, E2E_PORT_BASE 6170.

## Global Constraints

All of the index plan's Global Constraints, plus:

- Title formats, exact (`·` is U+00B7, `●` is U+25CF): lobby `Hearts · 2 of 4 players` (4 is `tableLimit`); in game and after it `Hearts · 4 players`; your turn `● Your turn · Hearts · 4 players`; vote waiting on you `● Vote · Hearts · 4 players` (vote wins over turn). Spectators and table screens get the plain form. The landing page keeps `Multiplayer Tabletop Games`.
- Notification text, exact, and nothing else (no hand, no tile, no private piece): turn `Your turn` / `<Game> · <gameId>`; vote `A vote is waiting for you` / `<Game> · <gameId>`; game over `Game over` / `<winner names joined by ", "> won <Game>` or `Draw in <Game>`.
- Votes that alert a seat: `undoVote` and `dismissVote` the seat is connected for and has not answered (dismiss: not its target), `rematchVote` without the seat's answer, `handRequests` whose `seat` is the seat.
- Notifications only fire when you are not looking at the game. Spectators and table screens never get notifications.
- No new packages. Payload-less push only (no message encryption). The VAPID contact comes from the optional `PUSH_CONTACT` environment variable (a `mailto:` or `https:` URL), read in `server/server.ts` beside `PORT`, default `mailto:admin@localhost`, documented in the README.
- Every Notification, service worker and push call is guarded: missing APIs, plain http and a denied permission degrade to tab titles only and never throw into the game page.
- The server only sends pushes to endpoints on known push services: hosts ending in `.googleapis.com`, `.mozilla.com`, `.push.apple.com`, `.notify.windows.com`, over `https:`, at most 1000 characters. Anything else is refused at subscribe time.

## Review Focus

1. Plain http (`http://192.168.x.x:3000`), or a browser without `Notification`, `serviceWorker` or `PushManager` (iPhone Safari in a tab): the game page loads and plays, the setting explains why it is off, titles still change (Task 4, Task 5).
2. A seat freed in a lobby, or a game deleted after the empty timeout, and a new player taking the same game ID and seat: they never receive the old player's pushes (Task 3).
3. The server restarts: no push storm on the first rejoin for alerts that were already true (Task 3).
4. A push service answering 404/410 (expired subscription) or timing out: the endpoint is dropped or skipped, play is not delayed, and nothing throws out of `broadcast` (Task 2, Task 3).
5. A vote that opens while the seat's own tab is visible sends no push and no notification; one that opens while hidden shows exactly one notification even if both the page and a push would fire (same tag, Task 3, Task 5).

### Task 2: VAPID keys and push sending with node:crypto

**Files:**
- Create: `server/vapid.ts`, `server/vapid.test.ts`, `server/pushStore.ts`, `server/pushStore.test.ts`

**Interfaces:**
- Produces in `server/vapid.ts`:
  - `type VapidKeys = { publicKey: string; privateJwk: JsonWebKey }`, `publicKey` the base64url of the 65-byte uncompressed P-256 point (0x04, x, y), as `applicationServerKey` wants.
  - `createVapidKeys(): VapidKeys` with `generateKeyPairSync('ec', { namedCurve: 'prime256v1' })` and JWK export.
  - `vapidHeaders(keys: VapidKeys, endpoint: string, subject: string, nowMs: number): Record<string, string>` returning `Authorization: vapid t=<jwt>, k=<publicKey>`, `TTL: '86400'`, `Urgency: 'high'` (the caller adds `Topic`). The JWT: header `{"typ":"JWT","alg":"ES256"}`, claims `{ aud: new URL(endpoint).origin, exp: floor(nowMs / 1000) + 12 * 3600, sub: subject }`, signed with `crypto.sign('sha256', data, { key, dsaEncoding: 'ieee-p1363' })`.
  - `isPushEndpoint(value: unknown): value is string` with the host list from Global Constraints.
  - `sendPush(endpoint: string, headers: Record<string, string>, fetchImpl = fetch): Promise<'sent' | 'gone' | 'failed'>`: POST, empty body, 10 s `AbortSignal.timeout`; 404 and 410 are `gone`; errors are `failed` and logged once, never thrown.
- Produces in `server/pushStore.ts` (its own `DatabaseSync` on `DATABASE_PATH`, so `GameStore` and its fakes do not change):
  - `openPushStore(file: string): PushStore` with tables `settings (key TEXT PRIMARY KEY, value TEXT NOT NULL)` and `push_subscriptions (room_id TEXT, seat INTEGER, endpoint TEXT, PRIMARY KEY (room_id, seat, endpoint))`.
  - `type PushStore = { getSetting(key: string): string | null; setSetting(key: string, value: string): void; add(roomId: string, seat: Seat, endpoint: string): void; endpoints(roomId: string, seat: Seat): string[]; removeSeat(roomId: string, seat: Seat): void; removeRoom(roomId: string): void; removeEndpoint(endpoint: string): void; roomIds(): string[] }`
  - `loadVapidKeys(store: PushStore): VapidKeys`: reads setting `vapid`, else creates, stores and returns new keys.
- [ ] **Step 1: Write the failing tests:**

### Task 3: The server sends alerts on change

**Files:**

**Interfaces:**

- New client messages in `MESSAGE_TYPES`: `PUSH_SUBSCRIBE` `{ endpoint: string }`, `PUSH_UNSUBSCRIBE` (no payload), `SET_VISIBLE` `{ visible: boolean }`. Seats come from the connection, never the payload. Spectator and table screen connections are refused with `Only players get notifications`.
- `Connection` in `server.ts` gains `visible: boolean`, true on join.
- Produces in `server/alerts.ts`:
  - `createAlerts(deps: { store: PushStore; keys: VapidKeys; subject: string; games: GameInfo[]; send?: typeof sendPush; now?: () => number })` returning:
    - `roomChanged(roomId: string, views: Map<Seat, BasePublicState> | null, visibleSeats: Set<Seat>): void`. `null` (room gone) removes the room. Otherwise: seats no longer in `activePlayers` are removed from the store; the first call for a room only records each seat's alert key (no push, so a restart never re-sends); later, a seat whose key changed to a non-null alert and is not in `visibleSeats` gets one push per endpoint, with the `Topic` header set to the first 32 base64url characters of a sha256 of the room ID; after a `gameOver` round the room's subscriptions are removed. Sending is fire-and-forget; `gone` removes that endpoint.
    - `pending(endpoint: string): { title: string; body: string; tag: string; url: string }[]`: the latest alert per room for that endpoint since the last call, then cleared. `tag` is the room ID; `url` is `joinLink('', gameType, gameId)`. Move `joinLink` unchanged from `src/services/share.ts` to a new `shared/links.ts` and re-export it from `share.ts`, since the server may not import `src/` (add `shared/links.ts` to this task's files).
- `server.ts`: opens `openPushStore(DATABASE_PATH)`, `loadVapidKeys`, `PUSH_CONTACT`; after `createGameManager`, removes stored rooms whose `manager.getState(roomId)` is undefined; `broadcast(roomId)` ends with `alerts.roomChanged(roomId, viewsByActiveSeat, visibleSeats)` inside a try/catch that logs; `hooks.removed` calls `alerts.roomChanged(roomId, null, new Set())`. Routes: `GET /api/push/key` gives `{ publicKey }`; `POST /api/push/alerts` with `express.json({ limit: '2kb' })` takes `{ endpoint }` and gives `{ alerts: pending(endpoint) }` (an unknown endpoint gets an empty list).
