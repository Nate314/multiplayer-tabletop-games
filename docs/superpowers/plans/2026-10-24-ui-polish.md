# UI Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Share links that open the join dialog, a searchable and filterable landing page with a grid on wide screens, a fixed-size History dialog with a speed choice and a settings gear, and checkboxes and selects themed like the buttons.

**Architecture:** Pure logic goes in small tested modules (`src/services/share.ts` for links and sharing, `src/components/gameFilters.ts` for the landing page, `src/components/fitScale.ts` and `playback.ts` for the History dialog), with remembered choices in `src/services/settings.ts`. Components stay thin: `ShareButton`, `GameFilters` and `PlaybackSettings` are new; `App`, `GameList`, `GameView`, `HistoryDialog` and `useGameConnection` change. The shared control looks are `:where()` defaults in `src/App.scss` that read the `--platform-*` variables, falling back to the lobby palette.

**Tech Stack:** React 19, Vite 6, TypeScript, SCSS (sass), Express 5, `node --test`, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-24-ui-polish-design.md`

## Global Constraints

- No new dependencies
- Styles in SCSS, matching PR #21 (`src/App.scss` stays flat with `:where()` selectors; a game's rules stay nested in its `[data-game="<id>"]` block)
- Shared control styles live in `src/App.scss` under `:where()`, like the other platform defaults, so the preferences and house rules PRs can use them when combined
- This branch must not depend on the house rules, preferences or drag and drop branches; "when combined" items are hook points only
- Check every changed layout at phone width (375 px, and 320 px for the game header) and at least one wide width (1280 px), in light and dark mode, for overlap, blank rows and misplaced controls
- Unit tests for filtering and link parsing; e2e tests for the share link, filters and the History gear
- `docs/architecture.md` and `README.md` are updated in the task that changes the behavior they describe
- Never use em-dashes in any prose (docs, comments, commit messages)
- Test style: `node:test` with `node:assert/strict`, next to the code; match each file's semicolon style (`settings.ts` has none, `src/components/*.ts` and `shared/` use them). e2e uses `test`, `expect`, `newPlayer`, `joinGame`, `nameOf` from `e2e/fixtures.ts`
- Do not commit to master; this plan runs on `scss-migration` or a branch made from it

## Review Focus

1. Sharing on plain `http://<server-ip>:3000` (the README's LAN setup): no `navigator.share` and no `navigator.clipboard`, so neither path works. Expect the link shown in a selectable field to copy by hand, never a silent failure. Test: Task 4, `share falls back to a link to copy by hand when the clipboard fails`.
2. Opening a share link in a tab that is still in a different started game: today's automatic rejoin would throw the player back into the old game and drop the link. Expect the link's join dialog, with the old game offered by the "Back to ..." button. Test: Task 3, `a link to another game wins over the automatic rejoin`.
3. Remembered filters that hide every game, or the game a player is looking for, on a later visit. Expect "No games match these filters" and a visible Clear filters button whenever a filter is on. Test: Task 6, `filters are remembered after a reload and Clear filters shows every game again`.
4. A move animation inside a scaled-down History board: `slideFrom` measures in screen pixels but translates inside the scaled board, so a piece would start from the wrong place. Expect it to start from its old square. Test: Task 7, `slideOffset divides the distance by the board scale`.
5. Cancelling the system share sheet: expect nothing to happen (no "Link copied", no copy). Test: Task 2, `a cancelled share sheet does not copy`.

### Task 2: Join links and sharing logic

**Files:**
- Create: `src/services/share.ts`
- Test: `src/services/share.test.ts`

**Interfaces:**
- Produces:
  - `export type JoinLink = { gameType: string; gameId: string }`
  - `export function joinLink(origin: string, gameType: string, gameId: string): string` returns `${origin}/join/${encodeURIComponent(gameType)}/${id}`, where `id` is `encodeURIComponent(gameId)` with every `.` also written as `%2E`: `serveClient` answers 404 for any path with an extension, so `/join/chess/v1.2` would never reach the app
  - `export function parseJoinLink(pathname: string, gameTypes: readonly string[]): JoinLink | null`: matches `/join/<type>/<id>` with an optional trailing slash; decodes both parts; `null` for any other path, an unknown game type, an empty ID, or a malformed `%` escape (catch `URIError`). The ID is kept as decoded (the join dialog's 20-character `maxLength` and the server's checks still apply on Join)
  - `export type ShareTarget = { share?: (data: ShareData) => Promise<void>; clipboard?: { writeText(text: string): Promise<void> } }`
  - `export type ShareResult = 'shared' | 'copied' | 'cancelled' | 'manual'`
  - `export async function shareGame(target: ShareTarget, data: { title: string; url: string }): Promise<ShareResult>`: with `share`, call it; resolved is `'shared'`, a rejection named `AbortError` is `'cancelled'`, any other rejection falls through to the clipboard. With `clipboard`, `writeText(url)`; resolved is `'copied'`. Anything else (missing or rejected) is `'manual'`

  - `export const DEFAULT_FILTERS: LandingFilters = { search: '', sort: 'category', categories: [], players: null }`

- Produces (in `settings.ts`): `loadLandingFilters(): LandingFilters` and `saveLandingFilters(filters: LandingFilters): void`, key `landingFilters` in `localStorage`. Each field is checked on load and falls back to its `DEFAULT_FILTERS` value; unknown category ids are dropped; `players` must pass the same 1 to 99 whole-number rule
