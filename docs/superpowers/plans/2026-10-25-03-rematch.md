# Rematch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Any player can press Rematch on the game-over screen. Every player answers Join or Drop, and anyone who does not answer can be removed by the dismiss vote, which counts as Drop. Then the room becomes a fresh lobby at the same ID, with the joiners seated, last game's house rules as the proposal, and the spectators still watching. Each finished game is archived for 90 days, and history and game files open only for the people who were in that game.

**Architecture:** The finished game is archived in a new sqlite table the moment it ends, under `<gameType>/<gameId>#<n>`, so it outlives both the rematch reset and the room. The rematch vote lives in the room state (`rematchVote`) next to the undo and dismiss votes. When it settles, the manager builds a new lobby with `createGameState` and `addPlayer`, and reports the seat changes through a manager hook, so `server/server.ts` can move each socket to its new seat. History and game-file routes take a credential in the `Authorization` header and check it against the room's or the archive's seat keys, spectator keys and device hashes (`seatDevices`).

**Tech Stack:** TypeScript, node:sqlite, node:crypto, Express 5, ws, React 19, node:test, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-25-spectators-social-and-new-games-design.md`, feature 3. Index plan: `docs/superpowers/plans/2026-10-25-spectators-social-and-new-games.md`. Branch `rematch` from `spectators-social` after wave 1, so plan 1 (spectators: `spectators`, `spectatorKeys`, `handRequests`, `privateSeatView`, `spectatorView`) and plan 2 (game-over: `GameResult`, `onGameFinished`, `gameNumber`, `GameOverDialog`, `canRematch`) are merged. PORT 3103, E2E_PORT_BASE 6150.

## Global Constraints

All of the index plan's Global Constraints, plus:

- `RematchVote` is exactly the index contract: `{ requestedBy: Seat; votes: Record<Seat, boolean> }`, `true` Join, `false` Drop. The archive key is exactly `archiveId` from plan 2's `GameResult`.
- Spectators and table screens never vote and never see Rematch (plan 2's `canRematch`). Hand permissions start fresh in the new lobby: every `allowedSeats` is `[]` and `handRequests` is `[]`.
- Archive retention is exactly 90 days from `finishedAt`: `ARCHIVE_TTL_MS = 90 * 24 * 60 * 60 * 1000`.
- Any request to `/api/history` or `/api/game-file` without a valid credential, for an unknown game, or for an archive past 90 days gets the same answer: 404 `{ "error": "This game is not available" }`, so an outsider cannot tell which games exist.
- The raw device ID never reaches a view, history, file or log. The server keeps only `hashDeviceId(id)`.

## Review Focus

1. The server restarts mid-vote: the vote is cleared (like undo and dismiss votes today), the archive is already saved, and the game-over screen offers Rematch again (Task 4 test). Nothing can be left waiting forever.
2. A player who stops answering, connected or not, is removed by the dismiss vote and counted as Drop, and the finished game's standings and archive do not change (Task 4 test).
3. A joiner who is disconnected when the vote settles: a lobby holds no disconnected seats, so they are left out and told so in the status. They can join again through the link (Task 4 test).
4. A game ID reused after its room was deleted: `n` continues from the archive, so an old archive is never overwritten (Task 2 test).
5. Secrets in responses: no history or file response contains any seat key, spectator key or device hash, and a spectator's file holds only the seats they were allowed (Task 3 test).

  - `server/devices.ts`: `hashDeviceId(raw: unknown): string | null`, null unless `raw` is a string of 16 to 64 characters from `[A-Za-z0-9-]`, otherwise its SHA-256 hex (`node:crypto`). These are plan 10's exact name, file and rule, built here first; plan 10 reuses them and adds `samePerson` matching for linked devices.
  - `BaseGameState.seatDevices?: Record<Seat, string>` (plan 10's name), stripped in `publicView` with `seatKeys` and `spectatorKeys`. `JOIN_GAME`'s `deviceId` (the index contract field; plan 10 adds the browser side) is read in `handleJoinGame` and passed to `join` as a seventh parameter after plan 1's `role`: `join(gameType, gameId, playerName, rejoin?, seatKey?, role?, deviceId?)`.   - `access(state: BaseGameState, credential: string | undefined): { kind: 'player' } | { kind: 'spectator'; allowedSeats: Seat[] } | null` in `server/games.ts`. A match on a `seatKeys` value or on `hashDeviceId(credential)` in `seatDevices` is a player; a match on a `spectatorKeys` value is that spectator, with `allowedSeats` taken from `state.spectators`. Compare with `crypto.timingSafeEqual` on equal-length buffers.
  - `history(gameType, gameId, credential, n?)` and `gameFile(gameType, gameId, credential, now, n?)`. Without `n` they read the live room; with `n` they read `loadArchive(\`${type}/${id}#${n}\`)`, building views with the same `historyMoments` and `historyStep` code as the live room. Both return `{ error: 'not-available' }` when the game is missing or `access` is null. History steps are the table view (viewer `null`) for every caller. A player's file has `views` for every seat, as today. A spectator's file has `views` only for their `allowedSeats` (a table screen's is `{}`).
  - Routes: `GET /api/history/:gameType/:gameId/:n?` and `GET /api/game-file/:gameType/:gameId/:n?`. `n` is a positive integer, anything else is not available. The credential is `Authorization: Bearer <credential>`. Not available is 404 `{ error: 'This game is not available' }`; a live game not over is still 409 for the file.
  - Client: `useGameConnection` returns `credential: string | undefined`, its `seatKey` ref, which for a spectator holds the spectator key (plan 1 sends it in `GAME_JOINED.seatKey`). `App` passes it to `GameView` and on to `useHistoryDialog(gameType, gameState, client, credential)`, which sends the header on both fetches.

### Task 4: The rematch vote and the reset into a lobby

**Files:**
- Modify: `shared/types.ts`, `shared/messages.ts`, `server/games.ts`, `server/games.test.ts`, `server/server.ts`

**Interfaces:**
- Produces:
  - `type RematchVote` (index contract) in `shared/types.ts`; `BaseGameState.rematchVote?: RematchVote | null`.
  - Messages: `REQUEST_REMATCH` (no payload), `VOTE_REMATCH { join: boolean }`, and server to client `LEFT_GAME { message: string }`.
  - `ManagerHooks.reseated?: (roomId: string, moves: Reseat[]) => void` with `type Reseat = { from: Seat; to: Seat | null; seatKey: string }`, called during a reset before the result returns.
  - `requestRematch(roomId, seat): Result<BasePublicState>`: refused with `'The game is not over yet'`, `'A rematch vote is already in progress'` or `'A vote is already in progress'` (undo or dismiss open). Opens `{ requestedBy: seat, votes: { [seat]: true } }` with status `'<name> wants a rematch'`.
  - `voteRematch(roomId, seat, join: unknown): Result<BasePublicState>`: `join` must be a boolean (`'Invalid vote'`); `'No rematch vote in progress'`; `'You already voted'`. Records the answer, then settles.
  - Settling, once every seat in `activePlayers` (connected or not) has answered: no connected joiner clears the vote with status `'Nobody joined the rematch'` (Rematch can be pressed again; since the requester counts as Join, this happens when everyone else drops while the requester is disconnected). Otherwise `archiveRoom`, then the new state: `createGameState(gameId)`, `gameNumber + 1`, `houseRules` with the old `values` and `maxPlayers`, `agreed: []` and `revision` one higher, then `addPlayer` for each connected joiner in old seat order (so seats run 1..k and the game's own first-player rule applies through `resetLobby`), each keeping its `seatKeys` entry and `seatDevices` entry under its new seat. `spectators` and `spectatorKeys` are kept, with every `allowedSeats` set to `[]` and `handRequests` to `[]`. `history` and `timeline` are emptied and the timers cleared. A joiner left out because they were disconnected is named in the status (`'Bob was not connected and was left out'`). Then `reseated` reports every old seat.
  - Undo and dismiss: `requestUndo` is refused with `'A rematch vote is in progress'`. During a rematch vote, `requestDismiss` may target any seat with no answer, connected or not, other than the requester. Its voters are the connected players other than the target. When it passes, the target's vote becomes `false` and no seat is removed, so the finished game is untouched, and then the rematch settles.
  - `loadRoom` clears `rematchVote` with the other votes.
  - `server/server.ts`: routes the two messages (a spectator connection gets plan 1's "Spectators cannot do that"); `reseated` moves each connection to its new seat and sends `GAME_JOINED` with the new `playerNumber`, the same `seatKey` and the lobby view, and sends `LEFT_GAME { message: 'You left after the game' }` to a connected socket whose seat became null, then forgets that connection. Spectator connections stay as they are.
