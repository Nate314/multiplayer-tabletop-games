# Open Games List Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** With `SHOW_OPEN_GAMES=true`, the landing page lists the games happening now ("Alice in the lobby", "Alice, Bob currently playing Chess") with their IDs, refreshing on its own; tapping one opens the join dialog filled in. Without it, nothing changes and the server has no such route.

**Architecture:** The game manager gains `openGames()`, which builds a list of plain fields (never a state object, so no secret can ride along). `server/openGames.ts` mounts `GET /api/open-games` only when the variable is on, and `serveClient` stops answering unknown `/api/` paths with `index.html`, so "off" is a real 404. The client polls the route every 5 s from a "Games happening now" section above the game list and stops for good on the first 404.

**Tech Stack:** Express 5, React 19, SCSS, node:test, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-25-spectators-social-and-new-games-design.md` (feature 5). Index plan: `docs/superpowers/plans/2026-10-25-spectators-social-and-new-games.md`. Branch `open-games` from master, PORT 3105, E2E_PORT_BASE 6190.

## Global Constraints

All of the index plan's Global Constraints, plus:

- The variable is read once in `server/server.ts` next to `PORT`: `const SHOW_OPEN_GAMES = process.env.SHOW_OPEN_GAMES === 'true';` Any other value, including `1`, is off. The README documents exactly `SHOW_OPEN_GAMES=true`.
- Copy, verbatim: section heading `Games happening now`; lobby line `<names> in the lobby`; playing line `<names> currently playing <game name>`; names joined with `, `.
- A listed entry carries only `gameType`, `gameId`, `players` (names) and `playing`. Never a seat key, spectator key, device ID or any state field.

## Review Focus

1. A seat key, or any other state field, reaching `/api/open-games` because a whole state was spread into the entry: Task 1 asserts the exact key set and that no seat key string appears in the JSON.
2. The variable off, but the SPA fallback answering `/api/open-games` with `index.html` and a 200, so the route looks "served": Task 2 pins a 404 for unknown `/api/` paths.
3. A started game whose players have all disconnected still listed (nobody can play it), or a game waiting on one disconnected player dropped from the list: Task 1.
4. A long or odd player name (20 characters, `<b>`) breaking the row at 320 px or rendering as markup: React text only, and the browser check uses a 20 character name.
5. The list refreshing while the join dialog is open steals focus or reorders under the finger: the section keeps rendering but the dialog is a separate overlay, checked in Task 4's e2e by joining after a refresh tick.

### Task 1: `openGames()` on the game manager

**Files:**
- Modify: `shared/types.ts` (add `OpenGame`), `server/games.ts` (new manager method)
- Test: `server/games.test.ts`

**Interfaces:**
- Produces: `type OpenGame = { gameType: string; gameId: string; players: string[]; playing: boolean }` in `shared/types.ts`. `players` are the names of `activePlayers` in seat order (dismissed players are gone, disconnected ones stay). `playing` is `state.started`.
- Produces: `openGames(): OpenGame[]` on the manager. Skips rooms with `isGameOver`, and started rooms where `connectedPlayers(state).length === 0`. Order: lobbies first, then games in progress; within each, by `gameType`, then `gameId`. The client sorts by display name itself if it wants; the server order only needs to be stable.

### Task 3: Fetching and wording on the client

**Files:**
- Create: `src/services/openGames.ts`, `src/services/openGames.test.ts`

**Interfaces:**
- Consumes: `OpenGame` (Task 1), `GameInfo` from `shared/gameDefinition.ts`.
- Produces:
  - `OPEN_GAMES_REFRESH_MS = 5000`.
  - `fetchOpenGames(): Promise<OpenGame[] | 'off' | 'failed'>`: `'off'` on a 404 (the server does not list games), `'failed'` on a network error, other status or a body without a `games` array; entries that are not `{ string, string, string[], boolean }` are dropped.
  - `describeOpenGame(game: OpenGame, gameName: string): string`, the exact copy from Global Constraints.
  - `joinRoleFor(game: OpenGame): 'player' | 'spectator'`: `'spectator'` when `playing`. These two literals are members of plan 1's `JoinRole`, so after the merge the value passes straight to the join dialog.

- [ ] **Step 1: Write the failing tests** with a stubbed `globalThis.fetch`:
  - `describeOpenGame` gives `Alice in the lobby` for `{ players: ['Alice'], playing: false }` and `Alice, Bob currently playing Chess` for two names, `playing: true`, `gameName: 'Chess'`.
  - `joinRoleFor` is `'player'` for a lobby and `'spectator'` for a game in progress.
  - `fetchOpenGames` returns `'off'` for a 404, `'failed'` for a 500 and for a rejected fetch, the list for `{ games: [...] }`, and drops `{ gameType: 'chess', gameId: 1 }` from a mixed list.

### Task 4: "Games happening now" on the landing page

**Files:**
- Create: `src/components/OpenGames.tsx`, `e2e/openGames.spec.ts`
- Modify: `src/App.tsx` (render it in `lobby-main` above `<GameList>`, and an `onSelect` that fills the dialog), `src/App.scss` (styles next to `.lobby-actions`), `e2e/fixtures.ts` (a worker option for server env), `docs/architecture.md` (Client: the section; Server: the route and the `/api/` 404)

**Interfaces:**
- Consumes: Task 3's functions, `GAME_INFOS`.
- Produces: `<OpenGames games={GameInfo[]} onSelect={(game: OpenGame) => void} />`. It polls `fetchOpenGames` on mount and every `OPEN_GAMES_REFRESH_MS` while `document.visibilityState === 'visible'` (and once more on `visibilitychange` to visible), stops for good on `'off'`, keeps the last list on `'failed'`. It renders nothing while the list is empty, off or not loaded. Otherwise `<section className="open-games" aria-labelledby="open-games-heading">` with `<h2 id="open-games-heading">Games happening now</h2>` and a `<ul>` of `<button type="button" className="open-game">`, each showing the game's server icon (`ServerSvg`, `svgUrl('game-icon', id)`, as `GameList` does), the game name, `ID <gameId>` and the `describeOpenGame` line. Entries for a game type not in `games` are skipped. Key: `${gameType}/${gameId}`.
- App: `onSelect` calls `setGameId(game.gameId)` then `openDialog(game.gameType)`. Player or Spectator preselection is integration work after plan 1: App passes `joinRoleFor(game)` as the dialog's initial role. On master the dialog has no role, so a game in progress opens as a plain join (the server answers that the game has started, which is today's behavior).
- `e2e/fixtures.ts`: add a worker-scoped option `serverEnv: [{} as Record<string, string>, { scope: 'worker', option: true }]`, spread into the spawned server's `env` after `process.env`. Other specs are untouched.
