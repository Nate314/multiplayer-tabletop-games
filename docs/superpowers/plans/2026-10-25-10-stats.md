# Stats Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Stats page showing records from the finished games this browser's private device ID played in, with clearing your own data and linking devices by a one-time code.

**Architecture:** Each browser makes a random `deviceId` and sends it with every join. The server keeps only its SHA-256 hash, on the seat (`seatDevices`, stripped from every view like `seatKeys`) and in a `devices` table mapping hashes to an internal person ID. `onGameFinished` writes one `results` row and one `result_players` row per seat. Stats endpoints take the device ID in a POST body, resolve it to a person, and return only results that person played in, with names, places and scores but no IDs; the client aggregates them into the page's sections.

**Tech Stack:** node:sqlite, node:crypto, Express 5, React 19, node:test, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-25-spectators-social-and-new-games-design.md` (feature 10). Index plan: `docs/superpowers/plans/2026-10-25-spectators-social-and-new-games.md`. Branch `stats` from `spectators-social` after wave 2 (game-over with `onGameFinished` and `GameResult`, rematch with the archive, pass-and-play, table screen merged). PORT 3110, E2E_PORT_BASE 6290.

## Global Constraints

All of the index plan's Global Constraints, plus:

- The raw device ID never leaves the browser except in a join or a stats request body. It is never in a URL, a log line, a view, a history step, a game file, the open games list, a stats response or the database. The database holds `sha256(deviceId)` hex only, and stats responses hold neither the hash nor the person ID.
- `GameResult.players[].deviceId` (index contract) carries the hash, not the raw ID. Plan 3's archive check for "players after the room is gone" must hash the presented ID with `hashDeviceId` and resolve it through `samePerson` (Task 1), so a linked device also counts.
- Names group case-insensitively (`name.trim().toLowerCase()`), shown in the spelling of the most recent game.
- Recorded: every finished game with at least one seat that has a device, and not abandoned. Abandoned: `moveCount === 0`, or fewer than 2 seats still active when it ended (everyone else left or was dismissed). Spectators and table screens are never recorded. A pass-and-play device records each of its seats under its one device.
- Copy, exact: "Former player"; clear confirm `This removes you from <n> games on <k> devices. It cannot be undone.` with buttons `Clear my data` and `Cancel` (an in-page panel, never `confirm()`); link panel `Link another device`, `Open this link or enter the code on the other device. It works once, for 10 minutes.`; link errors `That code has expired or was already used`, `This device is already linked`.
- Link codes: 7 characters `XXX-XXXX` from `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (no 0, O, 1, I, L), valid 10 minutes or one use, kept in memory (shortcut: a restart voids open codes, fine for a 10 minute code).
- QR code: reuse plan 9's in-house QR SVG asset (look in `shared/svg/` and `server/assets/registry.ts` for `qr`). If it is not on the branch, stop and report the dependency rather than adding a second encoder.

## Review Focus

- Plain http on a home network: `crypto.randomUUID` is missing outside a secure context, so the device ID is made with `crypto.getRandomValues` and works on `http://<ip>:3000` (Task 3).
- Storage blocked: the page still loads and shows "No games yet", and joins send an ID kept for the page's life (Task 3).
- A device cleared from another linked device: its next stats request answers `cleared`, it makes a new ID, and nothing from its old ID is recorded afterwards, even a game that was running during the clear (Task 1, Task 2).
- A game finished before this change, or a room saved without `seatDevices`: it records with no person for those seats and never throws inside `onGameFinished` (Task 2).
- Same-name players who are different people at different tables ("Sam" from two groups): stats group by name only within the games you played, which is the spec's rule; the page says "People are matched by name" under People (Task 4).

### Task 1: Device hashes and the stats store

**Files:**
- Create: `server/devices.ts`, `server/stats/store.ts`
- Test: `server/devices.test.ts`, `server/stats/store.test.ts`

**Interfaces:**
- Produces:
  - `hashDeviceId(raw: unknown): string | null` in `server/devices.ts`: `null` unless `raw` is a string of 16 to 64 characters from `[A-Za-z0-9-]`; else the SHA-256 hex.
  - `openStatsStore(file: string): StatsStore` in `server/stats/store.ts`, a second `DatabaseSync` connection to the same `DATABASE_PATH` (`':memory:'` in tests), creating if missing:
    - `people (id INTEGER PRIMARY KEY AUTOINCREMENT)`
    - `devices (hash TEXT PRIMARY KEY, person_id INTEGER NOT NULL)`
    - `cleared_devices (hash TEXT PRIMARY KEY)`
    - `results (id INTEGER PRIMARY KEY AUTOINCREMENT, archive_id TEXT UNIQUE NOT NULL, game_type TEXT NOT NULL, game_id TEXT NOT NULL, started_at INTEGER NOT NULL, finished_at INTEGER NOT NULL, move_count INTEGER NOT NULL)`
    - `result_players (result_id INTEGER NOT NULL, seat INTEGER NOT NULL, name TEXT NOT NULL, place INTEGER NOT NULL, score TEXT, person_id INTEGER, PRIMARY KEY (result_id, seat))`, `person_id` null for a seat without a device or a Former player.
  - `type StatsStore = { record(result: GameResult): void; resultsFor(hash: string): StatsGame[] | 'cleared'; deviceCount(hash: string): number; clear(hash: string): { games: number; devices: number }; link(fromHash: string, toHash: string): { games: number } | { error: string }; samePerson(hash: string, hashes: string[]): boolean }`.
  - `type StatsGame = { archiveId: string; gameType: string; gameId: string; startedAt: number; finishedAt: number; moveCount: number; historyAvailable: boolean; players: { name: string; place: number; score?: string; you: boolean }[] }` in `shared/stats.ts` (the client reads it too). `historyAvailable` is filled in Task 2.
  - `record` is idempotent on `archive_id`, skips abandoned results and those with no device, creates a person for an unknown hash, and stores a cleared hash's seat as Former player. `clear` renames the person's seats to "Former player" with `person_id` null, deletes results left with no person, moves every device hash of the person to `cleared_devices` and returns the counts it removed. `link(from, to)` (from: the device that used the code, to: the code's owner) moves `from`'s person's rows and devices onto `to`'s person.

- [ ] **Step 1: Write failing tests**: `hashDeviceId('a'.repeat(32))` is 64 hex characters and stable; `hashDeviceId('short')`, `hashDeviceId('x'.repeat(65))`, `hashDeviceId('a b'.repeat(8))` and `hashDeviceId(5)` are null. Store tests with fixed hashes A, B, C:
  - `resultsFor(A)` lists a game A and B played with `you` true only on A's seat; a game only C played is absent.
  - a pass-and-play result with seats 1 and 2 both A gives two players with `you` true.
  - recording the same `archiveId` twice gives one row; `moveCount: 0` and `abandoned: true` record nothing.
  - after `clear(A)`, `resultsFor(B)` shows A's seat as `Former player` with `you` false, `resultsFor(A)` is `'cleared'`, and a later `record` with A's hash stores Former player.
  - `link(B, A)` returns B's game count, then `resultsFor(B)` equals `resultsFor(A)` and `deviceCount(A)` is 2; `link(A, A)` errors `This device is already linked`; `clear(B)` afterwards clears both and reports `devices: 2`.
  - every table's columns, dumped with `SELECT * FROM <table>` after the scenario above, never contain the raw IDs used to make A, B and C.

- [ ] **Step 3:** Implement; every write in one transaction, as `server/store.ts` does.
- [ ] **Step 4:** `npm test` passes.

**Interfaces:**

- Produces, pure in `src/stats/aggregate.ts`, each taking `StatsGame[]` already filtered:
  - `filterGames(games, { gameType: string | null; range: 'month' | 'all' }, now: number): StatsGame[]` (`month`: since the first of this calendar month, local time).
  - `peopleStats(games): { name: string; games: number; wins: number; winRate: number; favoriteGame: string; streak: number }[]`, Former player left out, win means place 1, streak counts the person's most recent consecutive wins (0 after a loss), favorite is the most played game type (ties to the most recent).
  - `gameStats(games): { gameType: string; played: number; usualMinutes: number; highScore?: { score: number; name: string } }[]`, usual length the median of `finishedAt - startedAt` in whole minutes; `highScore` the largest leading number in a `score`, only when in every result of that game type a place-1 player holds the largest score (so Hearts shows none).
  - `headToHead(games, a: string, b: string): { games: number; aWins: number; bWins: number; other: number }`, over games both names played.
- The page (`.stats-page`): filters (game select with "All games", This month / All time), then People, Games, Head to head (two name selects from People), Recent games (newest 20: game name, date, players with places, a History link only when `historyAvailable`), and at the bottom `Link another device` (code as text, the link `/link/<code>`, the QR code, a countdown to expiry) and `Clear my data` with the confirm panel. A `cleared` answer or a finished clear calls `replaceDeviceId()` and shows "No games yet". `/link/<code>` shows `Link this device?` with the code and a `Link` button, then the Stats page.
