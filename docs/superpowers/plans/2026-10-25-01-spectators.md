# Spectators Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Anyone can join a game as a spectator, watch the whole table, and see a player's hand once that player allows it, with nothing private leaking in any game.

**Architecture:** Spectators live in the room state (`spectators`, `spectatorKeys`, `handRequests`), so they survive a restart. Which spectators are connected is kept only in memory on the room, the way sockets are. A spectator's view is the table view (viewer `null`) plus `seatViews`, the `privateSeatView` of each seat they were allowed. Each game with private information defines `privateSeatView` by picking its seat-dependent fields from its own `toPublicState(state, false, seat)`, and one test over every game proves that the table view plus those fields equals the seat's own view. On screen a spectator gets the game's existing read-only `HistoryBoard`, which already draws a seat's hand when given a `viewer`.

**Tech Stack:** TypeScript, React 19, Express 5, ws, node:test, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-25-spectators-social-and-new-games-design.md`, feature 1. Index plan: `docs/superpowers/plans/2026-10-25-spectators-social-and-new-games.md` (Shared contracts, ports PORT 3101 and E2E_PORT_BASE 6110, delivery). Branch `spectators` from master.

## Global Constraints

All of the index plan's Global Constraints, plus:

- The contract names are exact: `JoinRole`, `Spectator`, `HandRequest`, `spectators`, `handRequests`, `spectatorKeys`, `spectatorView(definition, state, spectator)` in `shared/spectators.ts`, `GameDefinition.privateSeatView?(state, seat)`, `GAME_JOINED` with `playerNumber: null` and `spectatorId`. `JOIN_GAME.role` missing means `'player'`.
- Every new state field is optional, and a room saved before this change loads with none of them.
- A spectator never moves, acts, votes, sets or agrees to house rules: the server refuses each with "Spectators cannot do that".
- Copy, exactly: "Watching: Dana, Eli"; "Dana (watching) wants to see your hand" with "Allow" and "Don't allow"; join button "Join" or "Watch".
- This plan adds only the `'player'` and `'spectator'` roles to the switch. Plans 8 and 9 add the other two to the same control, so build it from a list.

## Review Focus

1. Undo after a spectator joined or was allowed: the restored state must keep today's `spectators`, `spectatorKeys` and `handRequests`, not the ones from before the move (Task 2).
2. A seat number reused in the lobby: a permission for seat 2 must never pass to whoever takes seat 2 next, so asking is refused until the game has started (Task 3).
3. A request left open forever: its spectator left, its seat was dismissed, the game ended, or the server restarted. Each drops it (Task 3).
4. Names: a spectator named like a seated player, or a player named like a spectator, in any case, is refused with "That name is taken in this game" (Task 2).
5. A history step, a game file or another player's view carrying a spectator key or someone else's hand request (Task 2, Task 3).

  - A spectator join needs an existing room ("Game not found"): watching never creates a game.
  - A name matching a seated player, or a spectator from a `'player'` join, is "That name is taken in this game". A wrong or missing key is "That name is taken in this game". `rejoin: true` with an unknown spectator name is "You are not in this game".

Add a `shortcut:` comment: departed spectators keep their slot so a refresh keeps its permissions; prune them if the cap is ever reached in practice.
  - `switchToPlayer` works only before the first move ("The game has started; keep watching until the rematch"). It removes the spectator entry and key, then seats them through the usual `addPlayer` path with the same name, so "Game is full" still applies.
  - `publicView` strips `spectatorKeys`, `handRequests`, `spectators` and `seatViews` along with `seatKeys`, so history steps and game files carry none of them. The live `view` adds back `spectators` (connected ones only, from `watching`) and `handRequests` (Task 3).
  - `resolveUndoVote` keeps the current `spectators`, `spectatorKeys` and `handRequests` on the restored state, as it does `playerNames`. `replaceState` keeps `spectatorKeys` as it keeps `seatKeys`.
  - A spectator join or leave saves the room (a started room's state is rewritten, with no step).
  - `startEmptyTimer` still counts only players: spectators alone never keep a game alive.

### Task 3: Hand requests

**Files:**
- Modify: `server/games.ts`
- Test: `server/spectators.test.ts`

**Interfaces:**
- Produces: `requestHand(roomId: string, spectatorId: string, seat: unknown): Result<BasePublicState>` and `answerHand(roomId: string, seat: Seat, spectatorId: unknown, allow: unknown): Result<BasePublicState>`.
- `requestHand` errors, checked in this order: no `privateSeatView` "Nothing is hidden in this game"; table screen "A table screen never asks"; `!started` "Wait for the game to start" (seats are only fixed then); over "The game is over"; seat not in `activePlayers` "That player is not in this game"; already allowed "You can already see that hand"; pending "You already asked". It appends `{ spectator, seat }`. It never touches `gameStatus`, since only those two people are involved.
- `answerHand` with no matching open request is "No request to answer". `allow === true` adds the seat to that spectator's `allowedSeats` (for the rest of the game). Either way the request is removed, so after a no the spectator can ask again.
- Views: a player sees only the open requests (`openHandRequests`) whose `seat` is theirs. A spectator sees only their own. `disconnectSpectator` removes that spectator's requests. `loadRoom` clears all requests, since nobody is connected after a restart.
